# Этап 2: пробный перенос ядра тюрьмы на Rust — итоги

2026-10-20. Эталон — gorn-tli 6d54eb0 (1.0.31), `src/core/prison`.

## Решение

**Идём дальше, но запас маленький.** Правило плана — «если доигрывание в
одном потоке быстрее TS меньше чем в 2 раза, полный переход ради скорости
не окупается». Доигрывание мгновенной стратегией (его крутит решатель)
получилось **в 2,1–2,4 раза** быстрее в переносимой сборке (её получат
игроки) и **в 2,9–3,2 раза** со сборкой под процессор этой машины;
случайными ходами — в 2,0–2,2 раза (со всеми 31 орудием худший прогон —
1,98×). Порог пройден, но по нижнему краю оценки «в 2–3 раза», а не с
запасом.

Что это значит на деле:

- Самоигра мгновенной стратегией, 200 000 забегов: TS — 31 с в одном
  потоке и 4,9 с на 16 процессах; Rust — 14–15 с в одном потоке и
  **1,4–1,8 с** на всех ядрах (rayon). Для бенчмарков разработки это
  в 2,7–3,6 раза быстрее лучшего, что даёт TS на этой машине.
- Мгновенный совет — 0,8 мкс против 1,8–2,1 мкс (в среднем). Игрок
  разницы не заметит, но решатель (этап 3) крутит его в каждом раунде
  Монте-Карло: столько же раз быстрее будут и раунды.
- Перенос оказался точным и недорогим: движок и стратегия перенесены
  строка в строку за один день и совпали с эталоном на миллионе сидов с
  первой попытки. Риск «Rust-версия тихо разойдётся с правилами» закрыт
  сверкой, которая гоняет 10⁶ забегов за минуту.

Почему не больше: эталон на TS уже выжат — состояние в Int32Array, ГСЧ без
упаковки чисел, ни одной аллокации в цикле. Явных потерь, которые Rust мог
бы убрать, там нет; остаётся общий выигрыш компиляции заранее против JIT.

Что можно выиграть сверх этого (для этапа 3, не сделано): сборка под
Zen 4 даёт ещё +38 % (см. ниже) — похоже на раскладку кода, а не на
инструкции, и это стоит проверить PGO на переносимой сборке; горячие
циклы по 16 камерам (`targets`, маски) просятся в SIMD вручную.

## Что перенесено

Cargo workspace (`Cargo.toml`), release: `lto = "fat"`, `codegen-units = 1`.

| Эталон (gorn-tli) | GornNext |
|---|---|
| `engine/rng.ts` | `crates/gorn-prison/src/rng.rs` — mulberry32, потоки по метке |
| `engine/state.ts` | `state.rs` — `[i32; SIZE]` с той же раскладкой, копия — memcpy |
| `engine/rules.ts` | `rules.rs` — строка в строку, порядок бросков и короткие замыкания сохранены |
| `engine/actions.ts` | `actions.rs` — коды ходов, `settle`, `legal_codes`, `apply_code`, `random_playout` |
| `policy/instant.ts` | `policy/instant.rs` — рабочие таблицы в структуре `Instant` (по одной на поток) |
| `policy/weights.ts`, `weights.json` | `policy/weights.rs`, `data/weights.json` (копия) |
| `model.ts`, `client-tables.ts` | `model.rs`, `tables.rs` — ид, `Params`, веса событий и орудий |
| — | `runs.rs` — забеги по сиду для самоигры, замеров и сверки |
| — | `crates/gorn-cli` — `bench`, `selfplay`, `verify` |
| — | `tools/reference.mts` — эталон из `../gorn-tli` через его tsx |

Мелочи, без которых бит в бит не сходилось бы (сделаны сразу):

- арифметика JS по модулю 2³² (`Math.imul`, `|0`, `>>>`) — `wrapping_*` над u32;
- броски `int`/`chance`/`rollTier` в f64 в том же порядке операций;
- `Math.max` стратегии — функция `jmax` с правилами JS для NaN и ±0;
- чтение `swapNew[5]` за концом Float64Array(5) в эталоне даёт NaN — в Rust
  у массива шестой элемент NaN;
- бросок с шансом 0 (`relockEvent`, `doorEvent`, `oneLessDoor`) съедает
  число ГСЧ, как в эталоне;
- веса из JSON читаются с точным округлением (serde_json `float_roundtrip`)
  и сверяются с эталоном до бита.

## Сверка

`gorn-cli verify` запускает `tools/reference.mts` в 16 процессах node и
сравнивает на лету. Забег сида g одинаков в обоих: тема g % 5, цель
⌊g/5⌋ % 5 (мгновенная стратегия) или случайная (случайные ходы); орудия
у случайных ходов по g % 4 — нет / 6 / все 31 / случайная маска.

| Проверка | Объём | Итог | Время |
|---|---|---|---|
| веса стратегии, биты f64 | 53 | совпадают | 0,1 с |
| ГСЧ: 16 `next`, `bits30`, `float`, `int`, `chance`, `s`, 3 потока по метке | 100 000 сидов | совпадает | 0,4 с |
| мгновенная стратегия: хеш (ход + состояние после каждого хода) и итог | 1 000 000 сидов | без расхождений | 38 с |
| случайные ходы: то же | 1 000 000 сидов | без расхождений | 13 с |
| мгновенная стратегия: состояние после каждого хода, поле в поле | 1 000 000 сидов, 72 758 126 состояний | без расхождений | 41 с |
| случайные ходы: то же | 1 000 000 сидов, 64 394 151 состояние | без расхождений | 17 с |

Сверка чувствительна: при порче одного числа (`coin_bonus` 2 → 3)
расходятся 569 из 2000 забегов стратегии, и verify показывает первое
расхождение — сид, номер хода, ход и поля (`TIER[8] TS 2 Rust 3`).

`cargo test` — без node: ГСЧ на 7 сидах и 24 зафиксированных забега
(13 стратегией по всем темам и целям, 11 случайными ходами) — снимки из
эталона в `crates/gorn-prison/tests/data`.

Совет по вызовам меряется таймером с шагом ~0,1 мкс (Rust) и
`performance.now()` (TS) — медиана и p95 там грубые, среднее по пакету
точнее. «Доигрывание стратегией» эталон в architecture.md оценивает
в ~180 мкс (замер 18.10 до последних правок), сегодня на той же машине — 155–164.

**Сборки под процессор.** `target-cpu=native` здесь — это `znver4`
(+38 %). Уровни x86-64-v2 (POPCNT, SSE4.2), v3 (AVX2, BMI) и v4 (AVX-512 —
те же инструкции, что у Zen 4) дают ровно базовую скорость (70 ± 1 мкс на
забег самоигры против 51 у znver4), `znver3` — тоже. Значит, выигрыш — от
модели настройки LLVM под Zen 4 (раскладка и выбор ветвлений), а не от
наборов инструкций; у игроков другие процессоры, поэтому ориентир —
базовая сборка. Проверить на этапе 3: PGO на переносимой сборке.

Размер `gorn-cli.exe` — 0,55 МБ.

## Как повторить

```
cargo build --release
RUSTFLAGS="-C target-cpu=native" cargo build --release --target-dir target/native
target/release/gorn-cli verify                         # 10⁶ сидов по хешу, 10⁴ целиком
target/release/gorn-cli verify --seeds 0 --rng 0 --full 1000000   # 10⁶ целиком
target/release/gorn-cli bench --selfplay 200000 --threads 0
node --import file:///<путь>/gorn-tli/node_modules/tsx/dist/loader.mjs \
  tools/reference.mts ../gorn-tli bench 200000          # то же в TS
```

TS на 16 процессах — 16 раз `reference.mts … selfplay <from> 12500`
параллельно, время по часам (запуск node с tsx — 0,15 с).
